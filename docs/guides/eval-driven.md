# 评估驱动开发

::: tip 这篇讲什么
AI 应用的质量没有"对错"那么分明，改 Prompt、换模型、调 RAG 到底好不好，不能靠感觉。这篇讲怎么用评测集和指标，让每一次改动都有据可依。
:::

## 一、为什么必须评估

AI 应用有个致命特点：**改一处，其他地方可能悄悄变差**。比如：

- 换了个更便宜的模型，准确率降了 5%，你不测根本不知道。
- 改了 Prompt 让某类问题答得更好，却让另一类问题答坏了。

没有评测，你的每次"优化"都只是感觉。有了评测，每次改动都能用分数说话。

## 二、建评测集：一切的基础

评测集是一批"有代表性的输入 + 参考答案"，例如：

```json
[
  {"question": "如何申请退款？", "reference": "登录后在我的订单里点击申请退款……"},
  {"question": "会员有哪些权益？", "reference": "会员享受免运费、专属客服……"},
  {"question": "你们公司地址在哪？", "reference": "北京市朝阳区……"}
]
```

**要点**：
- **有代表性**：覆盖高频问题 + 易错问题 + 边界问题。
- **量够**：至少 30~50 条起步，越多越有统计意义。
- **答案明确**：参考答案要能用来判断对错。

## 三、选指标：多维打分

不要只看"对不对"，AI 应用要多个维度：

| 维度 | 含义 | 怎么测 |
|------|------|--------|
| 正确性/相关性 | 答得对不对 | 和参考答案比对 |
| 忠实度 | 有没有胡编 | 回答是否忠于资料 |
| 延迟 | 快不快 | 记录耗时 |
| 成本 | 贵不贵 | 记录 token |

打分可以用规则，也可以用另一个模型（LLM-as-judge）做裁判。

## 四、跑回归：每次改动都测

把评测流程自动化，改一次跑一次：

```python
scores = []
for item in eval_set:
    answer = app.answer(item["question"])
    score = judge(item["reference"], answer)   # 打分
    scores.append(score)
print(f"平均分：{sum(scores)/len(scores):.2f}  (上次：0.87)")
```

**流程**：基线打分 → 改 → 重跑 → 对比分数 → 涨了就保留，跌了就回滚。

## 五、闭环：从"测"到"改"

评估的价值在于驱动改进：

1. 看评测里"低分"的 case，找出共性。
2. 针对性优化：改 Prompt、补知识、调 RAG 参数。
3. 把新发现的问题补充进评测集，防止复发。

这样形成一个"测 → 改 → 补评测集 → 再测"的正向循环。

## 六、常见坑

- ❌ **没评测集就上线** → 出了问题都不知道从哪开始查。
- ❌ **只看准确率** → 还要看忠实度（是否胡编）、延迟、成本。
- ❌ **评测集太旧** → 用户问题在变，评测集要持续补充更新。
- ❌ **改了不回归** → 改了必须立刻重跑评测，确认没退步。

## 七、小结

一句话：**没有评测，就没有优化。** 建好评测集、选对指标、每次改动跑回归，你的 AI 应用才能从"凭感觉调"变成"用数据迭代"。
